# Local-Only Mode and Natural-Language Quick Add Implementation Plan

## Overview

OpenTasks 1.2.0 will let a fresh installation enter the complete task application without configuring or authenticating with PocketBase, while retaining the existing one-cache account-isolation guarantees. A local-only user may later connect to a PocketBase account through an explicitly destructive operation in which the local snapshot is authoritative and replaces all data currently owned by that account on the server.

The same release will add a minimal Quick Add task-entry screen. Task surfaces will offer Quick Add or the existing full editor after the floating plus button is pressed; Quick Add accepts a title, infers a bounded set of English date, time, and recurrence phrases, shows the accepted inferences as removable chips, and saves through the existing task Action.

## Problem Statement

The current application is locally persisted but does not support a backend-free first launch. Task UI is mounted only after PocketBase authentication proves that the one Room cache belongs to a remote account. Repository writes, reminders, notification callbacks, Android widgets, background maintenance, Navigation 3 ViewModel lifetime, and account transitions all rely on that durable boundary, so bypassing the login screen without introducing an equally durable local boundary would reopen stale-data and callback races fixed by the 1.1.0 account work.

Task creation currently always opens the complete editor. That editor is appropriate for detailed tasks, but it is unnecessarily heavy when a user wants to capture a title such as “Submit report tomorrow at 3pm” or “Water plants every Monday.” OpenTasks also has no deterministic natural-language parser for converting those phrases into its existing deadline and recurrence fields.

## Confirmed Product Decisions

- Local-only mode provides the complete local feature set: tasks, categories, tags, notes, countdowns, imports/exports, attachments, reminders, calendars, and Android widgets.
- A local-only cache is durable across restarts and uses the same boundary epoch protection as a PocketBase cache. It is not represented as a fake authenticated PocketBase session and never initializes a PocketBase client.
- “Connect to PocketBase” is an explicit destructive replacement. After authenticating and reviewing account-owned server counts, the user confirms that the local dataset takes precedence. The operation hard-deletes every record owned by the destination account, verifies that its seven sync collections are empty, then seeds the preserved local snapshot. Data belonging to every other PocketBase account remains inaccessible and untouched.
- Normal in-app deletes remain synchronized tombstones. Owner-authorized PocketBase hard deletion is added only for the confirmed authoritative replacement executor.
- Once destructive replacement has started, the operation is resumable but not cancelable. Task UI remains hidden until the remote account exactly represents the local snapshot or the user retries after a reported failure.
- Quick Add is a new minimal screen selected from a task-creation chooser shown after the floating plus button on Matrix, Task List, Calendar, and Quadrant Detail surfaces. Notes and countdowns retain their existing direct plus-button behavior.
- Quick Add displays only a title input, inferred chips, Back, and Add. Category, priority, and fallback calendar date come from the surface that opened it; all remaining task fields use existing safe defaults.
- Natural-language recognition is deterministic, English-only in 1.2.0, offline, and limited to dates, times, and recurrence types OpenTasks already supports. It does not use AI, a network service, fuzzy matching, categories, tags, priorities, reminders, or arbitrary recurrence intervals.

## Solution Architecture

### Durable active-cache modes

Extend the existing durable cache boundary with an explicit `CacheMode` whose values are `POCKETBASE` and `LOCAL_ONLY`. Existing serialized bindings decode as `POCKETBASE` by default. A local binding uses a reserved non-secret local owner marker plus a positive boundary epoch; remote endpoint, server identity, and capability values remain absent or invalid for PocketBase use and are validated according to the selected mode.

Add `AccountSessionState.LocalOnly` rather than treating the local cache as an authenticated account. Both `LocalOnly` and `Authenticated` authorize normal task UI and local foreground/background mutations through one active-cache boundary helper. Only `Authenticated` authorizes PocketBase client activation and network synchronization.

The existing account mutation gate remains the single process-wide serialization boundary. Local-only startup, local-to-PocketBase replacement, repository writes, reminder rebuilds, widget reads, sync, and cache transitions must not construct additional production gates.

### Authoritative local-to-PocketBase replacement

Reuse the current detached authentication, complete owner-scoped inventory, transition marker, sync reset, and exact seed machinery. Add a separate `AuthoritativeServerReplaceExecutor` for the destructive pre-seed phase rather than weakening normal `SyncService` behavior.

The replacement protocol is:

1. While the local-only session remains active, authenticate a detached PocketBase client and read the capability plus complete paginated inventory for all seven owner-scoped collections.
2. Require server support for authoritative replacement and present active/tombstone counts, attachment count, endpoint, and destination account identity. Do not retain the password.
3. On confirmation, enter `AccountMutationGate` and re-read the complete owner-scoped inventory before committing any transition or deletion. Compare the endpoint, server identity, account identity, and an opaque fingerprint of the sorted collection/record identities and active/tombstone state with the preview. If anything changed, replace the displayed preview and require a new explicit confirmation.
4. Only after that comparison succeeds, persist a typed local-to-PocketBase transition and destination cache binding with a new epoch, place the authenticated token in the durable pending/active promotion flow, hide task UI, cancel account-bound reminders, and prevent normal sync.
5. Hard-delete the destination account’s records from a fresh structured owner-scoped inventory in reverse dependency order: `task_tags`, `attachments`, `tasks`, `tags`, `categories`, followed by independent `notes` and `countdowns`. Attachment record deletion must remove the corresponding PocketBase file.
6. Re-read every collection and require a complete empty owner-scoped inventory. A cross-owner record can never enter the inventory or delete request.
7. In one Room writer transaction, retain all local rows and attachment files, reset every row’s PocketBase ID and sync bookkeeping regardless of its current `isSynced` value, and change the durable sync mode to the existing exact-seed-pending state.
8. Seed in normal dependency order with `ServerSeedExecutor`, including local tombstones and attachment bytes, then require exact final inventory equality for active rows and tombstones.
9. Clear the transition only after exact verification, publish `Authenticated(ONLINE)`, rebuild reminders, refresh widgets, and allow normal sync.

The transition is the crash-recovery authority. Failure or process death before the empty verification resumes remote deletion. Failure after the seed marker commits resumes exact seeding. If final verification finds any divergence caused by another client adding, updating, or deleting a destination row, the transition returns to its destructive pre-seed phase. Retry re-deletes the complete owner-scoped destination, verifies it is empty, atomically resets sync metadata for the entire preserved local snapshot, and starts an exact seed again; it never relies only on `getUnsynced()` or deletes only unexpected rows. The UI warns users to close other clients, but correctness does not depend on that warning: the operation must never report success while the destination inventory diverges from the local snapshot.

### Quick Add parser and state

Add a pure shared `ParseQuickTaskInputUseCase`. It accepts the raw input, a stable local reference date/time captured for the screen, and task-creation context, and returns a cleaned title plus typed recognized tokens. The ViewModel, not the composable, owns parsing, accepted/dismissed tokens, validation, saving, and stale/double-submit protection.

Recognized phrases are limited to trailing, case-insensitive, token-bounded clauses so ordinary title prose is not stripped accidentally:

- Relative dates: `today`, `tomorrow`, and `in N days` for `N` from 1 through 365.
- Relative weeks: `in N weeks` for `N` from 1 through 52.
- Weekdays: full English weekday names. A non-recurring weekday resolves to the next occurrence; when today is named and an explicit time is still in the future, today is allowed, otherwise it advances seven days.
- Times: `at H am`, `at H pm`, `at H:MM am`, `at H:MM pm`, and unambiguous 24-hour `at HH:MM`. Invalid hours/minutes remain literal title text.
- Existing recurrence: `every day`/`daily`, `every week`/`weekly`, `every month`/`monthly`, `every year`/`yearly`, `every weekday`, and `every <weekday>`. `every <weekday>` maps to `WEEKLY` anchored on the inferred weekday; no new recurrence enum or interval is added.

Date and recurrence tokens may be combined with one time token. An explicit parsed date overrides the Calendar surface’s fallback date. A parsed time without a parsed or contextual date uses today when still future and tomorrow otherwise. Date-only inference is all-day and uses the existing 08:00 local storage anchor without creating a notification reminder. Timed inference is not all-day. Recurrence without an explicit start date selects the first strictly future valid occurrence using the same 08:00 default anchor. Explicit phrases are never silently moved merely because they describe a past instant; they create an overdue task and the chip communicates the resolved date.

Recognized chips are active by default, which constitutes visible acceptance. Removing a chip suppresses that exact token signature while it remains in the input, so the phrase remains literal title text. Editing the phrase invalidates the suppression and allows the changed token to be parsed again. Saving removes only active recognized spans, normalizes the remaining boundary whitespace/punctuation, and is disabled if the resulting title is blank.

`CacheBinding` always describes a PocketBase endpoint/server/account/capability tuple. `AccountSessionState` has no task-authorizing state without an authenticated account. `AccountTransition` describes account switch/logout phases but not local activation or destructive server replacement.

**Modifications**:

- Add a serialized cache mode with a backward-compatible PocketBase default and a reserved local owner identifier used by reminders, widgets, and delayed callback matching.
- Validate local and PocketBase bindings with separate invariants. A local binding must never satisfy PocketBase activation requirements.
- Add `AccountSessionState.LocalOnly(binding)` and shared helpers for obtaining the active binding and optional authenticated account.
- Add typed transition purposes for local clear and local-authoritative replacement. Local clear has explicit `PRE_RESET` and `FILES_PENDING` phases; replacement has the minimum phases needed to distinguish pre-delete replacement from exact seed activation. Existing serialized 1.1.0 transitions decode as the existing account-switch purpose.
- Extend `AccountRepository` with start-local, clear-local-data, prepare-replacement, confirm-replacement, and cancel-preparation operations. Cancellation is available only before destructive confirmation.
- Persist boundary mode, epoch, destination identity, and replacement phase through existing Room `app_settings`; no Room entity or schema version change is required.

**Current state**:

Session restore requires a token and remote cache binding before task UI and boundary-wrapped Actions become available. Independent callbacks restore only an authenticated remote session. The PocketBase provider assumes every cache binding is remotely activatable.

**Modifications**:

- Starting local-only mode adopts the existing unbound local cache, including a legacy pre-account cache, under a new local binding and epoch without clearing user data.
- Restoring a local binding succeeds without reading or refreshing an auth token, keeps PocketBase disconnected, and publishes `LocalOnly`.
- A local binding paired with a remote token or a PocketBase binding missing its required token continues to fail closed instead of guessing ownership.
- Generalize foreground and restore-capable boundary execution to active-cache semantics while retaining a strictly remote-only path for operations that require PocketBase.
- Migrate background/widget/reminder call sites to the active-cache entrypoint so local reminders, notification actions, imports, attachments, and widgets are authorized by local account marker plus epoch.
- Ensure PocketBase client activation, owner-scoped gateways, `SyncService`, account switching, and reauthentication explicitly reject local bindings unless executing the confirmed local-to-PocketBase transition.
- Preserve logout semantics for PocketBase sessions. Local-only Settings exposes Connect and Clear Local Data rather than pretending there is a remote logout operation.
- Implement Clear Local Data as an `AccountRepository` transition under the existing mutation gate. On confirmation, durably write and publish `LOCAL_CLEAR/PRE_RESET`; restore of that purpose must resume clearing and must never apply existing cancel-prepared behavior. Cancel reminders and pending sync, then atomically replace Room with the pristine unbound cache, clear the binding, and advance the marker to `LOCAL_CLEAR/FILES_PENDING`. That second phase retries attachment cleanup only. After cleanup succeeds, clear credentials/transition state, disconnect PocketBase, and publish `SignedOut`. If attachment cleanup fails after the Room commit, keep task UI unmounted and `FILES_PENDING` durable so restart/retry finishes cleanup instead of remounting `LocalOnly` against a deleted cache.

### 4. Resumable Authoritative Replacement Executor

**Files**:

- `composeApp/src/commonMain/kotlin/com/udnahc/opentasks/data/sync/AuthoritativeServerReplaceExecutor.kt` (new)
- `composeApp/src/commonMain/kotlin/com/udnahc/opentasks/data/sync/ServerSeedExecutor.kt`

- `composeApp/src/commonMain/kotlin/com/udnahc/opentasks/data/auth/AccountCacheResetter.kt`

**Current state**:

`ServerSeedExecutor` safely seeds only a previously verified empty destination and resumes by `localId`. Account switching clears the source cache before pulling the destination. Neither path preserves local data while deleting an already-populated destination.

**Modifications**:

- Introduce a replacement preview containing sanitized endpoint/account identity and complete owner-scoped counts; never expose tokens, passwords, filenames, or task content.
- Preserve the full local Room graph and attachment files throughout the replacement. Only sync metadata is reset after remote emptiness is verified.
- Hard-delete remote rows in deterministic reverse dependency order and aggregate safe failures without proceeding to seed while any remote row remains.
- Re-inventory on every resume rather than trusting a stale preview or saved list of PocketBase record IDs.
- Re-inventory under the mutation gate immediately before destructive commitment. Store an opaque preview fingerprint derived from the endpoint/server/account identity and sorted owner-scoped inventory identities/state; any mismatch refreshes the sanitized counts and returns to the confirmation UI without persisting the destructive transition.
- Commit destination binding, transition marker, replacement mode, and sync metadata reset in writer transactions appropriate to their crash authority. Task UI remains unmounted whenever a replacement marker exists.
- Reuse `ServerSeedExecutor` for dependency-ordered creation, attachment upload, conditional acknowledgement, local-ID recovery, and exact final inventory verification.
- Prevent normal pull-before-push sync, missing-row recovery, account switching, logout, manual Sync, or a second replacement from running while replacement is pending.
- On successful seed, promote the pending token, clear replacement state, publish the authenticated destination, rebuild reminders, and refresh platform surfaces under the new epoch.
- If final inventory differs because another client added, updated, or deleted a row, keep the transition pending and report a retryable replacement conflict. Retry returns to full owner-scoped deletion, verifies empty, resets sync metadata for every local row in one writer transaction, and performs a new exact seed; do not merge remote divergence into the authoritative local cache or trust prior `isSynced` acknowledgements.

## Technical Considerations

- **Layering**: Session and replacement state remain in data/domain boundaries; UI calls account Actions through `AuthViewModel`. Quick Add UI calls a screen ViewModel, the ViewModel uses the parser UseCase and existing `AddTaskAction`, and no ViewModel accesses a repository or DAO.
- **State and UI**: Active Navigation is keyed by every boundary epoch in both modes. Destructive replacement unmounts active task UI. Quick Add parse state belongs to its entry-scoped ViewModel; composables render projections and never parse text. Compact, medium, and expanded layouts share behavior.
- **Data and Time**: No Room schema migration is planned. Binding/transition JSON gains backward-compatible defaults in `app_settings`. Natural-language output stays in local millis until repositories convert it to UTC. Existing recurrence anchors, completion behavior, tombstones, and reminder identity remain unchanged.
- **Sync and Failure Modes**: Local writes retain normal unsynced metadata while the provider is disconnected. Authoritative replacement is a dedicated hard-delete exception, owner scoped and durably resumable. Normal sync cannot run during replacement. Empty verification precedes sync metadata reset and exact seed. Clock skew is irrelevant to the delete-then-seed replacement but remains a normal-sync limitation afterward.
- **Platform Impact**: Shared UI/domain behavior applies to Android, iOS, and desktop. Android widgets, WorkManager, alarms, boot, and notification actions must operate in local mode. iOS background/notification callbacks must accept a local boundary. Desktop continues to lack native reminder delivery but otherwise supports both features.
- **Security and Privacy**: Passwords remain request-local; tokens use current secure storage. Replacement previews contain only counts and account/endpoint identity. PocketBase rules, gateway owner injection, full pagination, and final inventory checks preserve cross-account isolation. Logs contain phases/counts only, never credentials, titles, attachment contents, filenames, or raw server bodies.

## Edge Cases Considered

### Local-only and replacement

- Fresh install with pristine Inbox starts locally without touching the network.
- An unbound legacy local cache is adopted locally rather than silently cleared.
- A valid PocketBase-bound cache with missing/rejected credentials cannot be relabeled local; reauthentication remains required.
- Local startup with a stray token fails closed and clears only invalid credential state, not the local dataset.
- Starting local mode, login, replacement, logout, switch, clear data, sync, and user writes serialize through the same gate.
- Canceling credential/preflight before confirmation leaves the local binding/data/reminders unchanged and clears pending credentials.
- Confirmation with zero remote rows still runs empty verification and exact seed.
- Remote collections containing only tombstones are still deleted before seed.
- Replacement of empty, single-row, large paginated, mixed active/tombstone, and attachment-bearing accounts uses complete inventories.
- Failure deleting any row blocks metadata reset and seeding; a retry reads a new complete inventory.
- Process death before deletion, midway through deletion, after empty verification, midway through seed, or before marker clearing resumes from durable state without exposing mixed task UI.
- Concurrent writes by another destination device prevent final success; unexpected rows are never pulled into the local authoritative snapshot.
- Concurrent destination adds, updates, or deletes after a partial seed force Retry through complete owner-scoped deletion, verified emptiness, and a full local sync-metadata reset before reseeding, so previously acknowledged local rows are recreated.
- Account B records remain unchanged while Account A is replaced, even if local IDs overlap.
- Attachment hard deletion removes remote files; local attachment files remain until upload succeeds.
- Local callbacks and widgets from the old epoch fail after conversion; remote callbacks from the new epoch work.
- Clear Local Data recovery at `LOCAL_CLEAR/PRE_RESET` performs the Room/binding reset, while `LOCAL_CLEAR/FILES_PENDING` performs only attachment cleanup; both converge to signed-out/pristine state rather than canceling like an account-switch preparation or leaving an active local binding pointing at cleared data.
- Manual Sync and connection-error status are absent in local mode.
- Pull-to-refresh is disabled in local mode and cannot display a successful network-refresh result; authenticated mode keeps the existing gesture.

### Quick Add and parsing

- Empty, whitespace-only, or input composed entirely of active inference tokens cannot save.
- A normal title with words such as “Tomorrow” away from the recognized suffix remains literal.
- Invalid time/date/number ranges remain title text and never crash or clamp silently.
- Multiple date/time/recurrence clauses resolve deterministically while preserving unselected text.
- Dismissing a chip keeps its phrase in the saved title; changing that phrase makes it eligible for parsing again.
- Calendar context supplies a date only when the title does not infer one; title inference wins explicitly.
- Matrix/Task List/Calendar/Quadrant context produces the same defaults as the existing full editor.
- Weekday resolution around Sunday/Monday, month/year boundaries, leap day, daylight-saving transitions, and times equal to the reference minute use civil-date operations.
- Explicit past dates/times remain explicit and produce overdue tasks; implicit time-only/recurrence anchors choose a future occurrence.
- Rapid typing is synchronous and cancellation-free; rapid Add/IME presses create at most one task.
- Back preserves no persisted draft beyond the Navigation entry, matching the minimal capture flow.
- Account conversion/switch while Quick Add is open disposes its ViewModel and rejects a stale save through the boundary epoch.
- English parsing behavior is identical on Android, iOS, and desktop regardless of UI locale; unsupported localized phrases remain literal titles.

## Type Definitions

- `CacheMode`: `POCKETBASE`, `LOCAL_ONLY`.
- `AccountSessionState.LocalOnly`: durable local binding with no authenticated account or token.
- `AccountTransitionPurpose`: existing account transition, local clear, or local-authoritative replacement, with the existing purpose as the backward-compatible default.
- `AccountTransitionPhase`: add local-clear `PRE_RESET` and `FILES_PENDING` values (or equivalently named purpose-specific values) to the existing serialized phase contract; startup recovery dispatches by purpose before applying existing account-switch phase behavior.
- `LocalServerReplacementPreview`: sanitized endpoint, account identity, server identity, protocol support, per-collection active/tombstone counts, and an opaque owner-inventory fingerprint used only to detect changes before confirmation.
- `QuickTaskCreationContext`: category, priority, and optional fallback civil date.
- `QuickTaskTokenKind`: date, time, recurrence.
- `QuickTaskToken`: kind, source range/signature, resolved value, and active/dismissed state identity.
- `QuickTaskParseResult`: raw input, cleaned title, resolved local deadline, all-day flag, recurrence type, and recognized tokens.
- `QuickAddTaskUiState` and `QuickAddTaskSaveEvent`: entry-owned render/save state with one-shot consumption.

## Performance & Cost Impact

- Local-only startup removes network latency and performs the existing local initialization/reminder work.
- Parser work is linear in a short title and runs synchronously in the ViewModel; it introduces no background job, network request, database query, or recurring cost.
- Destructive replacement is intentionally expensive and proportional to the destination account’s complete record/file count plus the local seed size. It is user-initiated, serialized, paginated, and reports progress by phase/count rather than blocking the UI thread.
- Hard deletion of remote attachments transfers no file bytes, but reseeding uploads every preserved local attachment. The UI must warn that large attachment sets may take time and require a stable connection.
- No Room size increase or schema migration is introduced. Local-only unsynced tombstones may accumulate exactly as they do before a later server seed; cleanup is not added speculatively.

## Backward Compatibility

- Existing 1.1.0 `CacheBinding` and `AccountTransition` JSON decode as PocketBase/existing-transition mode through serialized defaults.
- Existing authenticated installations restore and sync unchanged after upgrade.
- Fresh or unbound installations gain “Use without sync”; no existing cache is automatically relabeled without the user selecting it.
- PocketBase capability version remains 2 so released 1.1.0 clients remain compatible. Version 1.2.0 requires `authoritativeReplaceVersion = 1` only when initiating destructive local-to-server replacement.
- PocketBase migration 012 broadens deletion only to the authenticated owner. Normal application deletes still call the existing tombstone paths.
- No Room migration or exported schema update is expected. If implementation proves a durable field cannot safely live in `app_settings`, the plan must return for user approval before introducing schema 13.
- Quick Add creates ordinary `Task` rows and sync records, so older clients can read them after synchronization.
