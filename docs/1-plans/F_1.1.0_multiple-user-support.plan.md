# Multiple-User Support Implementation Plan

## Overview

Add email/password account support for two pre-created PocketBase users while preserving OpenTasks' local-first behavior. Every synchronized record is owned by exactly one authenticated account, the client maintains one active Room cache per installation, and task UI is never rendered until the cache is proven to belong to the active account. The production cutover assigns all existing PocketBase data and any provably related legacy local cache to an explicitly supplied Account A; Account B starts empty.

## Problem Statement

The current app treats one PocketBase backend as a single trusted data space. Synced records have globally unique local IDs, requests are not owner-scoped, the local cache has no durable account binding, and startup enters task UI without an authenticated identity. Adding a second account without changing those boundaries could expose Account A's tasks to Account B through PocketBase queries, stale local Room rows, widgets, reminders, attachments, or background work.

## Solution Architecture

Use PocketBase's existing `users` auth collection as the identity authority and add a required `account` relation to every synchronized collection. The server enforces owner-only rules and composite `(account, localId)` uniqueness. The client owns a durable authenticated-session state machine, protected token persistence, and a `CacheBinding` proving which endpoint, server instance, account, capability version, and boundary epoch owns the single Room cache.

Login authenticates into a detached candidate session and validates server capability before exposing data. Switch and logout run behind one exclusive mutation gate: finish and verify source-account sync, invalidate reminders/widgets/background payloads, transactionally replace the Room cache and binding, then activate the destination token and perform its initial pull. Crash recovery uses the durable transition marker and binding as the authority, so the app never falls back to rendering the source cache after the destination binding has committed.

## Implementation Details

### 1. PocketBase Ownership Migration and Cutover Runbook

**Files**: `pocketbase/pb_migrations/011_add_account_ownership.js`, existing migration helpers under `pocketbase/`, and `docs/runbooks/pocketbase-multi-user-cutover.md`

**Current state**: `categories`, `tags`, `tasks`, `attachments`, `task_tags`, `notes`, and `countdowns` sync without account ownership. Existing `localId` uniqueness is installation-global and the metadata record identifies only the server instance/capability.

**Modifications**:

- Add a nullable single-relation `account` field targeting `users` to all seven sync collections, backfill every live row and tombstone to the exact operator-supplied `OPENTASKS_ACCOUNT_A_ID`, verify row counts and zero unowned records, then make the field required.
- Fail closed unless Account A and Account B are distinct valid user IDs, exactly two users exist for this first cutover, the legacy endpoint is a valid canonical URL, existing ownership does not conflict, and migrations through `010` are present.
- Replace global `localId` uniqueness with collection-specific composite unique indexes on `(account, localId)`. This permits both accounts to use the stable Inbox local ID.
- Set collection rules so list/view require authentication and stored ownership, create requires request ownership equal to the auth record, and update requires the submitted account to equal the stored owner while preserving the existing last-write-wins `localUpdatedAt` guard. PocketBase 0.36.7 supports relation-field `:changed`, but owner equality plus mandatory account injection remains the intentional, verified immutable-owner wire contract. Delete remains unavailable because tombstones are used.
- Keep public CRUD/list/view on the `users` collection locked while retaining password authentication.
- Upgrade `opentasks_sync_meta` to capability version `2`, retain `serverInstanceId`, and record immutable `legacyOwnerAccount` and canonical `legacyEndpoint`. Allow authenticated read-only access.
- Protect the attachment file field and require a valid PocketBase file token for downloads.
- Make the migration's down path explicitly reject rollback after account-specific writes can exist; operational rollback restores both database and storage backups instead.
- Document the exact PocketBase version, maintenance/freeze procedure, database and storage backup, restored disposable-instance proof, manual creation and verification of both accounts, environment inputs, pre/post counts, permission probes, protected-file probes, rollback, and client rollout sequencing.

### 2. Account and Cache-Binding Contracts

**Files**: new files under `composeApp/src/commonMain/kotlin/com/udnahc/opentasks/data/auth/`, account domain files under `domain/`, and settings persistence helpers under the existing data/settings package

**Current state**: PocketBase endpoint and server identity are stored, but the cache is not bound to an authenticated user and no account session state gates application data.

**Modifications**:

- Add `AuthenticatedAccount` containing only non-secret account identity/display metadata.
- Add `CacheBinding(canonicalEndpoint, serverInstanceId, accountId, capabilityVersion, boundaryEpoch)` with an atomically persisted representation.
- Add `AccountSessionState`: `Restoring`, `SignedOut`, `Authenticated` with online/offline freshness, `Transitioning`, and `ReauthenticationRequired`.
- Add a durable transition record with source/destination account IDs, endpoint/server identity, boundary epoch, and phases `Prepared` and `NeedsActivation`.
- Define `AuthTokenStore` with active and pending slots. Passwords never leave the login request and are never persisted.
- Define `AccountMutationGate` as the one exclusive boundary for switch, logout, legacy adoption/reset, sync mutations, and user-visible writes that could race a boundary change.
- Add `AccountRepository`, `ObserveAccountSessionUseCase`, and focused `RestoreSession`, `Login`, `SwitchAccount`, `Reauthenticate`, and `Logout` Actions. ViewModels consume only these UseCases/Actions.
- Keep installation-wide appearance, calendar, and other non-user preferences across account changes. Remove user-owned sync identity from generic preferences and persist it only through the binding/session contracts.

### 3. Platform Token Stores

**Files**: expected/actual contracts in common and platform source sets; Android implementation under `androidMain`; iOS implementation under `iosMain`; JVM implementation under `jvmMain`; dependency/version files only where required

**Modifications**:

- Android: encrypt tokens with an Android Keystore AES/GCM key and store ciphertext/IV in app-private preferences.
- iOS: store active and pending tokens in Keychain using an after-first-unlock, this-device-only accessibility class.
- macOS desktop: use the native login keychain through `java-keyring` (planned version `1.0.4`) and verify the packaged app can read, promote, and delete both slots.
- Windows/Linux desktop: use an app-private JSON token file with owner-only permissions where supported. Surface a concise sign-in warning that this fallback is weaker than native credential storage; never log token content.
- Make promotion from pending to active and clearing both slots idempotent so crash recovery can repeat safely.

### 4. Authentication, Startup, and Navigation Gate

**Files**: `composeApp/src/commonMain/.../ui/App.kt`, new account `AuthViewModel`, new login/account UI under `ui/screens/`, `SettingsViewModel`, settings UI, resources, and `di/AppModule.kt`

**Current state**: task navigation and task-scoped ViewModels can be created before an authenticated ownership boundary is established; endpoint editing lives in normal settings.

**Modifications**:

- Restore the secure token and durable binding before creating the main task navigation graph or task ViewModels.
- Render a session gate for restoring, signed-out/login, transitioning, reauthentication-required, and authenticated states. Key the authenticated Navigation 3 back stack by `boundaryEpoch` so an account boundary cannot retain prior-account screens or ViewModels.
- Signed-out login accepts email/password and an editable PocketBase endpoint. Canonicalize the endpoint, require HTTPS except for loopback and RFC1918 private-LAN endpoints, perform only an anonymous health check, authenticate into a detached PocketBase client, save the returned token in the pending slot, and validate authenticated capability and scoped inventory before activation. Private-LAN HTTP is an explicit operator tradeoff because credentials, tokens, and task data are not transport-encrypted.
- Keep the endpoint read-only while authenticated; require logout before changing it.
- Do not offer public signup, invitations, password reset, account administration, or shared tasks in v1.
- Confirmed auth rejection hides all task UI and enters same-account reauthentication. Connectivity-only refresh failures may continue in offline mode only when the durable cache binding already proves the active account.
- Add account identity plus switch/logout entry points to settings without placing passwords or tokens in UI state.
- Build compact, medium, and expanded login/session states with accessible focus order, keyboard submit, progress semantics, and resource-backed strings.

### 5. Safe Legacy-Cache Adoption

**Files**: account restore/adoption Action, settings/binding persistence, database transaction helpers, and focused tests

**Modifications**:

- If a legacy saved `serverInstanceId` exists, require an exact match with capability metadata. If it is absent, require the canonical saved endpoint and the build/default endpoint to match the metadata `legacyEndpoint`.
- Permit adoption only when the authenticated account equals metadata `legacyOwnerAccount` (Account A). Existing PocketBase record-ID matches are supporting evidence, never the sole ownership proof.
- Persist the new `CacheBinding` before allowing sync or rendering cached content.
- If ownership cannot be proven and the cache contains any unsynced row in the seven DAOs, block activation, keep task UI hidden, and direct the user to sign in as Account A. Never clear or upload those rows as Account B.
- If ownership cannot be proven but every row is synced, clear the cache under the mutation gate and initialize the selected account without rendering the old data.
- Treat a pristine Inbox-only cache as resettable for either account.

### 6. Owner-Scoped Sync Gateway

**Files**: PocketBase provider/client wrappers, sync gateway/service/coordinator/mode, inventory and seed/reset logic, all seven sync adapters, and attachment transfer code

**Current state**: adapters use endpoint-wide list/update behavior and decode records without independently validating an owner field.

**Modifications**:

- Make the active PocketBase provider derive its client/token/account only from authenticated session state.
- Route every production sync query through one structured owner-scoped gateway rather than ad hoc filter strings.
- Inject the active account relation into JSON and multipart creates/updates. Reject any raw response whose `account` differs from the active account before model decoding or DAO writes.
- Scope inventory checks, `localId` recovery, seed/reset decisions, deletion/tombstone handling, and degraded-sync comparisons by account.
- Identify a server/session with the tuple `(canonical endpoint, serverInstanceId, accountId)` while keeping `boundaryEpoch` stable during an authenticated session.
- Preserve dependency-ordered pull-before-push behavior and prevent another account's empty inventory from causing the current cache to seed or push.
- For protected attachments, request a file token per pull batch, retry once when token expiry is confirmed, and never log file URLs containing tokens or token values.
- Ensure sync reports expose safe account/boundary metadata sufficient to reject stale completion callbacks without exposing credentials.

### 7. Switch, Reauthentication, Logout, and Crash Recovery

**Files**: account Actions, Room transaction/reset helpers, reminder/widget boundary coordinator, attachment storage, and tests

**Modifications**:

- Switch first authenticates and validates a detached destination candidate against the same canonical endpoint, capability, and owner-scoped inventory. Selecting the current account becomes reauthentication rather than a destructive switch.
- Save the candidate token to the pending secure slot; do not replace the active token early.
- Under `AccountMutationGate`, refresh/sync Account A and verify zero unsynced rows across all seven DAOs. Block switching on failure; v1 has no discard-data path.
- Persist `Prepared`, clear/cancel account-bound reminders, notifications, widget projections, and background boundary payloads, then in one Room transaction clear user tables, recreate the pristine Inbox, reset sync bookkeeping, write Account B's binding with a new epoch, and advance the marker to `NeedsActivation`. Preserve installation preferences and endpoint.
- Clear account-bound attachment files, promote the pending token, replace the provider with Account B, perform an initial pull, rebuild reminders/widgets/navigation, and clear the transition marker.
- Crash before the Room transaction: source binding remains authoritative and the pending token can be dropped. Crash after the transaction: destination binding is authoritative and recovery promotes/validates the pending destination token. Never fall back to source data after the destination binding commits.
- Same-account reauthentication replaces the active token without clearing the cache after validating account, endpoint, and server identity.
- Logout requires online auth/sync and zero pending rows, then clears reminders/widgets/content/files/binding/tokens while preserving endpoint and installation preferences. Block logout if source data cannot be safely synchronized.

### 8. Reminders, Widgets, Notifications, and Background Work

**Files**: Android workers/widget/notification/reminder paths; iOS notification/background scheduler paths; shared boundary payload contracts; JVM no-op reminder implementation where applicable

**Modifications**:

- Include `accountId` and `boundaryEpoch` in every delayed, background, notification-action, alarm, and widget refresh payload that can outlive a foreground session.
- Reject stale payloads before reading or mutating task data.
- Android switch/logout clears pending and delivered notifications, ongoing reminder state, alarms, and reminder registry entries; widgets blank during transition and refresh only after destination activation. `SyncWorker` restores the authenticated session before syncing.
- iOS removes pending and delivered notifications for the source boundary and rejects stale notification/background callbacks after restore.
- Desktop retains its current no-op reminder behavior but participates in session restore and cache gating.

### 9. Documentation and Operator Guidance

**Files**: `README.md`, `docs/ARCHI.md`, `docs/ai/architecture.md`, `docs/ai/data-sync-time.md`, and the new cutover runbook

**Modifications**:

- Keep durable architecture rules in the focused docs rather than duplicating them in tool shims.

## Technical Considerations

- **Layering**: Shared session, ownership, transition, and sync policy stays in `commonMain`. ViewModels use account UseCases/Actions; repositories and the gateway wrap persistence/network details; native source sets own credential and notification APIs.
- **State and UI**: Task UI exists only inside `Authenticated`. Login callbacks carry an attempt identity and stale attempts cannot activate. Boundary-epoch changes recreate navigation and reject stale async/background events.
- **Data and Time**: Do not add `accountId` to every Room content entity or retain per-account databases. One transaction replaces the single cache. Existing UTC/local conversion, tombstones, recurrence, and sync ordering remain unchanged inside an account.
- **Sync and Failure Modes**: Pull remains dependency ordered and precedes push. Switch/logout block until source sync succeeds and all seven unsynced queries are empty. Network failure and authentication rejection have distinct states.
- **Platform Impact**: Android, iOS, macOS, Windows, and Linux require credential-store behavior. Android widgets/work and both mobile notification systems must be actively invalidated at account boundaries.
- **Verification and Security**: Authorization relies on PocketBase rules plus client-side raw owner validation and cache gating. Never persist passwords or log credentials/file tokens. A disposable real PocketBase instance is mandatory because mocks cannot prove migration/rule/file behavior.

## Edge Cases Considered

- Account A and Account B share the stable Inbox local ID without an index conflict.
- One account has no records while the other has many records and tombstones.
- Existing attachments remain owned by Account A and Account B cannot fetch their protected files.
- Login is retried rapidly, cancelled, or completed after a newer attempt; only the current attempt may activate.
- Startup is offline with a valid binding versus offline with no binding, mismatched endpoint/server, or an unfinished transition.
- Token refresh returns an authentication rejection versus a transient connectivity failure.
- Switch is requested while an edit, sync, reminder action, widget action, or attachment transfer is active; the mutation gate and epoch reject cross-boundary completion.
- The process exits before or after the Room replacement transaction and repeatedly retries recovery.
- Local legacy rows are unsynced, fully synced, or only the pristine Inbox, and the signing-in account is or is not the designated owner.
- Account A attempts to switch/logout while PocketBase is unavailable or LWW conflict resolution leaves pending rows; the operation remains blocked without a discard path.
- A protected-file token expires during a pull batch; the client retries once without leaking the token.
- Windows/Linux cannot enforce stronger-than-owner file permissions; login warns clearly and no password is stored.

## Type Definitions

- `AuthenticatedAccount`: stable PocketBase user ID, email, optional display name.
- `CacheBinding`: canonical endpoint, server instance ID, account ID, capability version, boundary epoch.
- `AccountSessionState`: restoring, signed out, authenticated online/offline, transitioning, reauthentication required.
- `AccountTransition`: source/destination identity, server identity, epoch, and durable phase.
- `AuthTokenStore`: read/write/clear active token, read/write/clear pending token, idempotent promote.
- `AccountMutationGate`: suspending exclusive operation around account-bound mutations.
- `AccountRepository`: detached auth, restore/refresh, capability validation, activate/deactivate session.

## Performance & Cost Impact

Owner filters and composite indexes keep remote queries bounded per account. Switches intentionally pay for a complete source synchronization and destination initial pull; this is a correctness boundary rather than an everyday interaction. One local cache avoids multiplying Room and attachment storage by the number of remembered users. Secure-store and epoch checks are small relative to sync/database work.

## Backward Compatibility

Old clients must be frozen before the migration because they cannot send ownership or interpret capability version 2. Production data is migrated exactly once to Account A with verified DB and storage backups. The client may adopt a legacy local cache only through the explicit server metadata proof; otherwise it safely clears only fully synced/pristine data or blocks on unsynced data. Rollback after Account B writes requires restoring the pre-cutover backup, not running a lossy down migration.
