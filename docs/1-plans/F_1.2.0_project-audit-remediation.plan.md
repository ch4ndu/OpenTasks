# Project Audit Remediation Implementation Plan

## Overview

OpenTasks 1.2.0 will remediate the actionable reliability, security, performance, lifecycle, test, and maintenance findings from the whole-project audit. The work hardens every external text/file boundary, closes temporary PocketBase and desktop-process resources deterministically, preserves coroutine cancellation, removes sensitive diagnostics and dead configuration code, makes recurrence/calendar projections bounded, keeps preview tooling out of release artifacts, and converts the current lint/deprecation backlog into an enforceable local quality gate.

This is a release-readiness plan for the already-unreleased 1.2.0 branch, not a new product feature and not a version-bump plan. Eleven findings are scheduled for remediation. The twelfth finding, the absence of CI, remains an explicit user-approved exception: no workflow files will be added and the plan must not claim that finding is fixed.

## Problem Statement

The audit identified the following concrete issues:

1. Android and iOS share payloads and Android/JVM/iOS CSV/ICS file imports can read unbounded external input. Android share parsing also performs stream I/O from the activity callback, while the iOS Share Extension mutates one payload from concurrent provider callbacks and embeds the entire payload in a custom URL.
2. `PocketBaseClientProvider` retains clients in strong companion maps and removes references without closing the underlying Ktor `HttpClient`; authenticator and replacement candidates can therefore leak resources.
3. Several suspending actions and ViewModels convert `CancellationException` into ordinary failures, allowing cancelled work to continue, log an error, or publish an incorrect UI error state.
4. `JvmCalendarProvider` does not reliably terminate timed-out `osascript` processes and can block while draining output before its timeout is effective.
5. Navigation keys and user-authored task, category, tag, note, countdown, URL, and content data can reach logs. The intended warning threshold for non-debug builds is disabled.
6. `PocketBaseAccountAuthenticator` has only classifier-level coverage despite owning password/refresh requests, capability validation, paginated owner inventory, boundary rejection, and error mapping.
7. The repository has no CI workflow.
8. Countdown recurrence projection advances one occurrence at a time with no useful bound, so an old daily or weekday anchor can consume unbounded CPU on a UI-facing projection path.
9. Settings retains an unreachable legacy PocketBase URL editor and three associated Actions; that path also defaults a scheme-less endpoint to HTTP.
10. Calendar composables still format dates/times and perform fixed list truncation during composition despite the ViewModel projection rule.
11. Compose UI tooling is present on the Android release runtime classpath.
12. Android lint reports 193 warnings, compiler output contains known deprecations, and the testing documentation requires a coverage-debt ledger that does not exist.

## Confirmed Decisions and Scope

- Remediate the eleven actionable findings above. Do not fold unrelated product/release constraints or general refactors into this plan.
- Retain the current iOS `opentasks://share` custom-URL handoff. Bound and validate it; do not introduce an App Group, shared container, temporary-file handoff, or migration framework.
- Do not add GitHub Actions or any other CI configuration. Finding 7 remains open by explicit user choice. Local verification remains mandatory.
- Keep new test code deliberately small. Add automation only when it is cheap to author and materially safer than manual verification; prefer extending an existing test file over adding a new harness or exhaustive matrix. Use a concise manual checklist for UI, native share, widget, Calendar automation, packaged-runtime, and live-service behavior when automation would be disproportionate.
- Do not add a disposable PocketBase server, multi-system integration harness, duplicated application bootstrap, emulator/simulator run, or physical-device flow without separate user authorization. The user will perform device/simulator/manual acceptance where needed.
- Use 1.2.0 in the plan filename because the current branch is the unreleased 1.2.0 feature branch. Do not change `versionName`, `versionCode`, `MARKETING_VERSION`, or build numbers in this work.
- Bring Gradle, AGP, compile/target SDK, Kotlin/KSP, Compose, AndroidX, and catalog dependencies to the latest compatible releases available during implementation. Apply upgrades in small coherent batches, read official migration notes for major/toolchain changes, compile after each batch, and keep a temporary pin only when a concrete incompatibility is reproduced and documented.
- No Room entity, DAO, schema, migration, PocketBase schema, sync protocol, reminder identity, or stored timestamp change is planned.

## Solution Architecture

### Bounded external-input contract

Add one common external-input policy used by Kotlin callers, with exact limits and typed rejection reasons. Imported CSV/ICS files may contain at most 5 MiB of UTF-8 bytes. System-share intake may inspect at most eight providers/stream URIs and may accept at most 32 KiB of decoded UTF-8 content across description, URL, ICS, and filename fields. The iOS custom URL itself may contain at most 64 KiB of UTF-8 bytes, and the received ICS filename may contain at most 255 UTF-8 bytes.

Every stream/file reader must stop after `limit + 1` bytes; metadata length checks are only an early rejection optimization because content providers can omit or misreport size. Oversized input produces a typed user-visible failure and is never parsed, imported, or placed in navigation state. The Swift extension mirrors the two share constants because it cannot consume common Kotlin constants, while the containing app revalidates the decoded payload so drift fails closed.

### Deterministic resource and coroutine lifetimes

`PocketBaseClientProvider` becomes the owner of every SDK client it creates. One internal release path removes endpoint/binding registry entries and closes the Ktor client exactly once. Active replacement constructs and validates the successor before publishing it, closes failed candidates, then closes the previous client after the new state is installed. Temporary authenticator sessions and detached replacement candidates use `try/finally` ownership.

Suspending call paths explicitly rethrow `CancellationException` before handling ordinary failures. Cleanup in `finally` may reset local loading/bookkeeping state, but cancellation must not be logged as failure, converted to a snackbar/error enum, treated as a failed attachment, or followed by additional repository/file mutations.

The desktop calendar shell uses a small injected process runner. It drains merged output concurrently, applies the timeout to the process lifetime, and destroys/forcibly destroys the child while closing all streams on timeout or coroutine cancellation.

### Safe diagnostics and testable account transport

Navigation diagnostics emit only a stable route name, never a serialized/key `toString()` value. User-entered titles, names, notes, descriptions, URLs, content samples, and content-shape metadata are removed from application logs. Debug builds retain useful structural diagnostics; non-debug builds set the global logging threshold to warning after the platform debug flag is initialized.

Authentication gains a narrow internal account-client session seam. Production sessions wrap a provider-owned PocketBase client and expose its Ktor client plus token update and close operations. A small number of tests supply a Ktor `MockEngine` session. The authenticator continues to own response decoding, capability validation, owner checks, and pagination; the seam exists to make the highest-risk wire and cleanup contracts testable, not to create a comprehensive server simulation.

### Bounded recurrence and calendar projections

Countdown projection computes an approximate recurrence index from the immutable original anchor and civil date distance, then performs only a small bounded correction around that candidate. Daily, weekly, monthly, yearly, and weekday recurrence keep existing interval and anchor semantics without replaying every historical occurrence.

Calendar domain/ViewModel projections carry preformatted row date/time text, all-day/timed classification, start minutes, fixed three-item all-day previews, fixed five-item month previews, overflow counts, selected-day labels, and the 24 timeline labels. Existing equality-based `scan` reuse remains so unchanged days retain stable list/projection identity. Only dynamic clipping whose limit is derived from measured pixel height remains at the layout boundary; it selects a prefix from an already sorted/projected list through a pure helper and performs no formatting, sorting, grouping, or model transformation in composition.

### Surgical maintenance gate

Delete the unreachable Settings URL mutation surface while retaining the durable `pocketbase_url` key, `ObservePocketBaseUrlUseCase`, authenticated sign-in/re-authentication, server migration, and account-state persistence.

Move UI tooling to debug-only dependency scope, update the toolchain and libraries to current compatible releases, resolve actionable resource lint warnings, and migrate deprecated APIs. Prefer a clean lint run without a baseline; if a latest-version warning remains because of a reproduced incompatibility, document the blocker beside the temporary pin and suppress only that exact warning until the blocker is removed.

## Implementation Details

### 1. External share and import boundaries

**Files**: `composeApp/src/commonMain/kotlin/com/udnahc/opentasks/ExternalInputPolicy.kt` (new), `composeApp/src/commonMain/kotlin/com/udnahc/opentasks/SharedTaskPayload.kt`, `androidApp/src/main/kotlin/com/udnahc/opentasks/MainActivity.kt`, `iosApp/ShareExtension/ShareViewController.swift`, `iosApp/iosApp/SharedTaskURLHandler.swift`

**Current state**:

- `SharedTaskPayload` represents only successful content and cannot publish a rejection to the mounted app.
- `MainActivity.publishShareIntent` parses synchronously; calendar streams use `readText()` and an unbounded URI list.
- The Swift extension flattens every provider, mutates one `SharedPayload` from concurrent callbacks, reads full strings/data/files, and constructs an unbounded URL.
- The iOS application handler trusts every decoded query value.

**Modifications**:

- Add the exact import/share/provider/URL/filename limits and typed `TOO_LARGE` and `TOO_MANY_ITEMS` outcomes to a common policy. Size means UTF-8 byte count, not Kotlin/Swift character count.
- Extend the shared payload event contract so native boundaries can publish either accepted content or a typed rejection with an event id; preserve id-based one-time consumption.
- In `MainActivity`, assign every incoming share a monotonically increasing parse generation and keep at most one parse job. A newer intent increments the generation and cancels the previous job. Capture small intent metadata promptly, move stream reads to `Dispatchers.IO`, check cancellation between bounded read chunks, and limit URI count and cumulative bytes.
- Immediately before every accepted or rejected publication, require both the captured generation to equal the current generation and the originating job to remain current/active. A cancelled blocking `ContentResolver` read that completes late must therefore discard its result rather than overwrite a newer intent.
- Preserve existing text/URL/ICS routing and URL extraction for accepted payloads. Do not accept images or arbitrary documents.
- In `ShareViewController`, reject more than eight providers before loading, collect provider results by source index, aggregate on one serialized queue in deterministic provider order, bound `String`, `Data`, and file-URL reads, and stop accumulating when the total limit is exceeded.
- Validate the fully percent-encoded URL against the 64 KiB limit. If collection or encoding is oversized, open a small `opentasks://share` error URL instead of embedding partial content.
- Inspect the `extensionContext.open` completion result. Complete the extension only when the containing app accepted the URL; when opening either an accepted or error URL returns false, keep the extension visible and show small extension-local failure feedback instead of silently reporting success.
- In `SharedTaskURLHandler`, reject an oversized raw URL before query parsing, reject decoded cumulative content/filename over the common contract, recognize only known error values, and publish the corresponding shared rejection. Unknown/malformed share URLs remain ignored.
- In `App.kt`, show a localized snackbar for typed share rejection, never navigate/import rejected data, preserve one-time clearing, and rethrow cancellation from shared ICS import instead of converting it to a generic failure.

**Files**: `composeApp/src/commonMain/kotlin/com/udnahc/opentasks/ui/util/CsvFilePicker.kt`, `composeApp/src/androidMain/kotlin/com/udnahc/opentasks/ui/util/CsvFilePicker.kt`, `composeApp/src/jvmMain/kotlin/com/udnahc/opentasks/ui/util/CsvFilePicker.kt`, `composeApp/src/iosMain/kotlin/com/udnahc/opentasks/ui/util/CsvFilePicker.kt`

**Current state**: All three file-picker implementations load the complete selected file. `FileImportResult.Error` has only an optional string, so callers cannot localize an oversized-file result safely.

**Modifications**:

Android/JVM decoders must report malformed and unmappable input rather than inserting replacement characters; Kotlin/Native uses the equivalent throwing decode, and Swift share reads use failable UTF-8 conversion. Use provider/file length metadata only for early rejection.

- Rethrow cancellation in coroutine-backed picker work; cancellation is not `FileImportResult.Error`.

### 3. Coroutine cancellation correctness

**Files**: `composeApp/src/commonMain/kotlin/com/udnahc/opentasks/viewmodel/TaskFormViewModel.kt`, `composeApp/src/commonMain/kotlin/com/udnahc/opentasks/domain/action/attachment/RemoveTaskImageAction.kt`, `composeApp/src/commonMain/kotlin/com/udnahc/opentasks/domain/action/settings/TriggerSyncAction.kt`, `composeApp/src/commonMain/kotlin/com/udnahc/opentasks/viewmodel/SettingsViewModel.kt`, plus the import/share files in section 1

**Current state**:

- Pending image save uses `runCatching`, so cancellation can be reported as a failed image.
- Attachment file deletion uses `runCatching`, so cancellation can be swallowed while later deletion steps continue.
- Sync and Settings operations catch broad `Exception`, log cancellation, and publish ordinary error states.
- Directly affected import/share callbacks also contain broad catches around suspending work.

**Modifications**:

- Replace coroutine `runCatching` blocks with explicit `try/catch` where necessary and always rethrow `CancellationException` first.
- Preserve best-effort handling for genuine attachment file I/O failures, but stop immediately on cancellation before any later file/repository mutation.
- Keep trigger-sync debounce/replacement semantics; a superseded or scope-cancelled sync is neutral and clears only its own pending-job reference.
- Ensure Settings manual sync and clear-local-data reset their operation state in `finally` without publishing `ERROR` for cancellation. For CSV/ICS export preparation, track whether `onReady` successfully handed the request to the platform launcher: cancellation or failure before handoff resets `exportInProgress`, while successful handoff deliberately leaves it set until `onExportResult` clears it and consumes `pendingExportCount`. The legacy URL-save catch disappears with section 9.
- Apply the same rule to file-picker, import ViewModel, and shared ICS work touched by section 1 so the new boundary path does not reintroduce the audit violation.

### 4. Effective JVM Calendar process timeout

**Files**: `composeApp/src/jvmMain/kotlin/com/udnahc/opentasks/data/calendar/JvmProcessRunner.kt` (new), `composeApp/src/jvmMain/kotlin/com/udnahc/opentasks/data/calendar/JvmCalendarProvider.kt`

**Current state**: Permission timeout leaves the child alive. Event fetching reads stdout to EOF before waiting, ignores the boolean timeout result, and may call `exitValue()` while the process is still running.

**Modifications**:

- Route both permission and event queries through the runner. Preserve public behavior: non-macOS is unavailable/empty, permission timeout/failure is denied, and event timeout/failure returns an empty list after safe diagnostic logging.
- Keep AppleScript construction, UTC/local conversion, parsing, and event mapping unchanged except where the runner result replaces direct `Process` access.

## Technical Considerations

- **Layering**: External-input policy and payload events live in shared common code. Platform readers implement native I/O only. ViewModels own UI-ready calendar/import state; composables render it. Existing Actions/repositories and account mutation gates remain the write boundary.
- **State and UI**: Shared payload events remain one-shot by id. Android combines cancellation with generation/current-job publication checks so late blocking reads cannot win. iOS aggregates provider results deterministically and keeps the extension visible on custom-URL open failure. Import/share rejection is localized. No new navigation destination, back-stack rule, retained timer, reconciliation loop, or persistence is introduced.
- **Data and Time**: No Room/PocketBase migration or timestamp representation changes. Recurrence uses civil dates and the immutable local anchor, retaining monthly/yearly clamp semantics. `kotlin.time.Instant` migration must preserve epoch conversions byte-for-byte.
- **Sync and Failure Modes**: Client closure must not alter cache binding, transition, pull-before-push ordering, offline restoration, exact seed, tombstone, attachment, or clock-skew behavior. Failed candidate setup leaves the current active client usable. Cancelled sync remains cancelled rather than a connectivity/auth failure.
- **Platform Impact**: Android share and picker reads use bounded background I/O plus stale-generation rejection. iOS extension and receiver both enforce the custom-URL contract and expose extension-local open failure. Desktop Calendar processes are killed on timeout, cancellation, or output overflow. Packaged JVM apps default to non-debug logging while the development run task opts in explicitly. Android widget metadata retains API-26 compatibility and API-31 launcher enhancements through resource variants.
- **Verification and Security**: No user content may reach logs. External data is rejected before expensive parsing/navigation. Ktor `MockEngine` proves the authenticator wire contract. Native compile checks are required; simulator/device execution and live services are explicitly unperformed unless separately requested.
- **Resource ownership**: Each provider-created PocketBase client and each spawned process has one owner and one close path. Closing a detached candidate cannot clear a different active client.
- **Upgrade/lint policy**: Maintain latest-compatible versions in small coherent batches. Prefer no lint baseline; any temporary pin, baseline entry, or suppression requires a reproduced blocker, narrow scope, and removal trigger.

## Edge Cases Considered

- Files and shares at exactly the limit are accepted; the first byte beyond the limit is rejected. Multibyte UTF-8 text is measured in bytes, and malformed/unmappable sequences are rejected rather than replaced.
- A content provider with unknown, zero, or dishonest metadata size still cannot bypass the bounded reader.
- Empty, malformed, unsupported-extension, invalid UTF-8, inaccessible, cancelled, and oversized imports remain distinct where the UI needs distinct behavior; platform exception text is not shown verbatim.
- Zero providers, one provider, eight providers, nine providers, multiple calendar streams, mixed text/URL/calendar providers, concurrent callback completion, repeated `onNewIntent`, and activity/extension cancellation cannot publish partial or stale payloads. A cancelled Android blocking read that completes late fails its generation/current-job check.
- Percent encoding can expand content; iOS checks both decoded content and final URL size. The containing app rechecks even when the extension accepted it. If `extensionContext.open` returns false for an accepted or error URL, the extension stays visible with local failure feedback.
- Closing a temporary client after success, parsing failure, HTTP failure, owner mismatch, or cancellation removes both registry entries. Releasing an old detached candidate after a new client activates must not close the new active client.
- A failed active-client candidate leaves the prior active endpoint, token, binding, and registry entries intact. Repeated disconnect/release is harmless.
- Cancellation during an attachment delete, pending-image save, sync debounce, export, import, or local clear does not emit a normal error or continue later destructive work. Export preparation resets before platform handoff on cancellation/failure, but successful handoff retains its guard until `onExportResult`.
- A child process that exceeds 16 MiB of merged output, exits non-zero, never exits, ignores normal destroy, or is cancelled while draining output is cleaned up. Empty/non-UTF output still maps to the provider's existing safe failure behavior.
- Route diagnostics for data classes with titles, descriptions, URLs, task ids, or countdown ids expose only the route type. Parser, Calendar import, authentication, and provider diagnostics expose no raw external date/time, timezone, calendar id, or endpoint.
- JVM development runs opt into debug logging explicitly; packaged applications omit the signal and initialize warning-or-higher logging.
- Auth tests cover one representative successful inventory flow, refresh token promotion, owner rejection, representative error classification, and failure/cancellation cleanup without an exhaustive permutation matrix.
- Daily/weekly recurrence spanning decades, weekday recurrence spanning weekends, monthly anchors on days 29-31, leap-day yearly recurrence, non-positive interval, a future anchor in count-up mode, and dates exactly on an occurrence preserve next/latest semantics.
- Removing the Settings editor does not remove endpoint display, sign-in, reauthentication, build-time default use during authentication, account-state persistence, migration, or local-to-PocketBase replacement.
- Empty calendar days, all-day-only/timed-only/mixed days, exactly-at-preview-limit, one-over-limit, compact/expanded height changes, today rollover, countdown rows, and unchanged day lists retain correct output and stable identities.
- Debug previews retain the tooling they need; the release graph must not. API-26 launchers/widgets keep base-compatible metadata while API-31 launchers receive preview/cell hints.
- Dynamic notification resources remain kept; genuinely unused resources are removed. Static widget preview sample content remains intentionally literal and compact.
- A major toolchain/dependency upgrade may require a source migration. Keep batches independently attributable and temporarily hold only the version with a concrete reproduced failure; compile/target SDK behavior changes are included in the user-owned Android manual checklist.
- The accepted CI exception remains visible even after every local command passes.

## Performance & Cost Impact

- External reads become O(configured byte limit) in memory/time and stop early. Accepted files still allocate their strictly decoded string once; oversized or malformed files never reach CSV/ICS parsing.
- At most one Android share job and eight native share items are active. iOS aggregation stores bounded per-provider results before deterministic merge.
- Client/process cleanup prevents native sockets, engines, streams, child processes, and captured Calendar output from accumulating without a bound across auth, account transitions, or repeated calendar checks.
- Countdown lookup changes from O(number of elapsed occurrences) to O(1) civil-distance arithmetic plus a fixed correction count.
- Calendar formatting/projection runs on `Dispatchers.Default` when source/today state changes rather than on every recomposition. Stable identity reuse limits downstream recomposition.
- Dynamic height clipping remains O(visible prefix) at layout time and does not duplicate sorting/formatting.
- Debug-only tooling reduces release dependency/artifact size. Lint/test changes have local build-time cost only.
- No hosted CI cost is introduced.
