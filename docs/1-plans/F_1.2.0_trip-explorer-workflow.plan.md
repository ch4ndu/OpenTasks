# Trip Explorer Workflow Implementation Plan

## Overview

Create one standalone project-local skill named `trip-explorer-workflow`. The skill will preserve the current TRIP planning experience, including direct user discovery, a detailed plan, an independent Sol `xhigh` adversarial plan review capped at five rounds, and explicit user approval before implementation. It will add one persistent, read-only Sol `high` Explorer that carries repository context from planning through implementation and review, while Luna `max` performs edits and independent Sol `xhigh` agents retain review authority.

This is internal workflow tooling tied to the repository's current 1.2.0 baseline; it does not change the OpenTasks application version or release contents.

## Problem Statement

The existing split TRIP flow has strong planning and verification gates, but its implementation phase repeatedly makes the manager reconstruct context and relay messages among implementation, review, repair, and final-verification agents. The new workflow should remove that avoidable relay work without weakening the planning phase, adversarial review, manager accountability, or user authority.

The user requested one skill only. Existing `trip-*` skills, runtime modules, installer/upgrade machinery, manifests, and base snapshots are outside this change.

## Scope Decisions

- The exact skill name is `trip-explorer-workflow`; the literal `**` placeholder is not part of the name because Codex skill names permit lowercase letters, digits, and hyphens only.
- The skill is project-local at `.agents/skills/trip-explorer-workflow/`.
- It is one continuous workflow that can stop after planning or continue, after explicit approval, through verified implementation.
- It directly uses the collaboration agent lifecycle rather than `.agents/trip/bin/launch_runtime.py`; no private runtime module or helper script is required.
- The normal endpoint is a verified implementation handoff. Commit, push, merge, tag, or release actions require separate explicit authorization and are never started automatically.
- The current `trip-1-plan`, `trip-2-implement`, `trip-3-release`, `trip-hotfix`, `trip-research`, `trip-review`, `trip-test`, `trip-init`, `trip-upgrade`, and `trip-compact` skills remain unchanged.
- One compact edit to existing project guidance is included because `AGENTS.md` requires durable workflow rules to be reflected in `docs/ai/*`. This is documentation for the one skill, not a companion skill or a wider workflow-suite change.

## Solution Architecture

The manager remains the only user-facing orchestrator and final completion owner. Five exact-model roles are used at different checkpoints:

| Role | Exact model and effort | Lifetime | Authority |
| --- | --- | --- | --- |
| Explorer | `gpt-5.6-sol`, `high` | One persistent thread from planning exploration through final evidence assembly | Read-only context and evidence steward; no verdicts or decisions |
| Plan reviewer | `gpt-5.6-sol`, `xhigh` | One independent thread reused for at most five plan-review rounds | Adversarial plan findings and approval verdict |
| Implementer/fixer | `gpt-5.6-luna`, `max` | One retained implementation thread after user approval | Edits only within manager-assigned ownership; cannot declare the task complete |
| Code reviewer | `gpt-5.6-sol`, `xhigh` | One fresh thread reused for at most five code-review rounds | Independent findings and review verdict |
| Final verifier | `gpt-5.6-sol`, `xhigh` | A new thread after code-review convergence | Fresh read-only completion verdict |

The manager adjudicates findings, protects scope, verifies the actual request, and communicates with the user. The user owns product decisions, plan approval, acceptance of unresolved findings, and authorization for any release or Git publication action.

```text
User request
    ↓
Manager ↔ persistent Sol-high Explorer (repository evidence)
    ↓
Detailed plan ↔ independent Sol-xhigh plan review (maximum 5 rounds)
    ↓
Explicit user plan approval
    ↓
Explorer implementation capsule → Luna-max implementation
    ↓
Explorer plan-to-diff delta → manager verification/testing
    ↓
Independent Sol-xhigh code review (maximum 5 rounds)
    ↓
Explorer evidence ledger → one consolidated Luna fix wave per round
    ↓
Fresh Sol-xhigh final gate
    ↓
Manager request verification and handoff; no automatic release
```

The Explorer is in the planning phase, but it does not sit between the user and manager. It supplies repository facts before and during plan drafting, source-checks disputed review claims, and prepares the approved-plan handoff. This adds context without adding another approval gate or another planning voice.

**Modifications**:

1. Add frontmatter with the exact name `trip-explorer-workflow` and a narrow description that triggers when the user explicitly requests this Explorer-assisted workflow. Do not make it the automatic handler for every coding request.
2. Add a preflight that rereads the latest request, `AGENTS.md`, all of `docs/ARCHI.md`, the task-relevant routed `docs/ai/*` files, the worktree status, and any existing approved plan. Preserve unrelated or user-owned changes.
3. Define two valid entry paths:
   - **New task**: run planning first.
   - **Resume from an approved plan**: reconstruct current context, re-create the exact Explorer if necessary, and continue only after confirming the plan was user-approved.
4. Spawn the Explorer once with agent type `explorer`, `fork_turns: "none"`, model `gpt-5.6-sol`, reasoning effort `high`, and one stable task name unique to this workflow. Give it the user request, repository paths, current phase, and the strict read-only role contract. Reuse the same agent with follow-up tasks until completion.
5. Fail closed if an exact requested model/effort cannot be created. Do not silently substitute another model, reuse the Explorer as a reviewer, or reuse a reviewer as the Explorer.
6. If the host session is in a read-only planning mode, keep the repository read-only and present the plan in chat. Do not create a branch, plan file, local state file, or implementation change until writes are allowed; if approval cannot be durably checkpointed, require renewed approval before a later implementation begins.

#### Planning contract

7. Preserve the current planning sequence rather than shortening it:
   - Direct manager/user discovery and clarification, with at most three rounds when blocking ambiguity remains.
   - Repository exploration before plan drafting.
   - A detailed file-level plan with scope, architecture, edge cases, verification, and explicit exclusions.
   - No production implementation before explicit user approval.
8. Bring the Explorer into planning after the request has enough shape for targeted investigation. Ask it for factual production paths, existing contracts, invariants, cross-platform consumers, relevant tests, contradictions, uncertainties, and decision points. Require file/symbol evidence and labels for fact, inference, uncertainty, and decision required.
9. Keep user-facing planning direct: the manager interprets Explorer evidence, asks the user only material product/architecture questions, and authors the plan. The Explorer may not silently choose product behavior, expand scope, edit the plan, or communicate as a second planner.
10. After the draft, spawn a separate plan reviewer using agent type `default`, `fork_turns: "none"`, model `gpt-5.6-sol`, reasoning effort `xhigh`, and a distinct stable task name. Seed it only with the latest user constraints and authoritative repository/plan paths; do not pass inherited Explorer conclusions. Retain that reviewer thread for the bounded review loop. The Explorer may source-check disputed repository facts, but the manager alone accepts or rebuts findings and revises the plan.
11. Use the exact plan-review verdict contract below. Every reviewer invocation consumes one of the five rounds, including a malformed response:
    - `APPROVED`: the plan-review loop converged.
    - `REQUEST_CHANGES`: adjudicate findings, revise the plan, and follow up with the same reviewer when available.
    - `NEEDS_REWORK`: stop the loop and surface the structural problem to the user; do not proceed to implementation.
    - Missing, duplicated, or malformed terminal verdict: fail closed and use the remaining budget to request a corrected verdict; never infer approval.
12. Preserve every plan-review finding in the workflow ledger. User-facing updates may consolidate resolved findings to avoid message relay, but any unresolved or decision-requiring finding must be surfaced with its original meaning and evidence. A substantive user-requested plan revision returns to the same reviewer and consumes the next remaining round; it never resets the five-round budget.
13. After review convergence, require explicit user approval and separate implementation authorization. If the user defers implementation, stop cleanly with the approved plan and durable state checkpoint as the handoff.

#### Persistent context contract

14. At plan approval, have the Explorer produce a compact implementation capsule containing:
   - Binding outcome, latest user constraints, and explicit exclusions.
   - Approved plan path and current repository snapshot.
   - Verified production paths, contracts, and invariants.
   - Plan acceptance criteria mapped to focused verification.
   - Protected/unrelated paths.
   - Material uncertainties and the bounded first Luna instruction.
15. Maintain one ignored state and handoff file at `.local/trip-explorer/<task-id>/context.md` for every workflow that can cross a user turn or session. Update it after each review round, each material implementation/fix wave, every explicit user decision, and before yielding at a phase boundary. It must record:
    - Latest request, binding constraints, exclusions, and current phase.
    - Plan path/hash plus explicit plan-approval and implementation-authorization evidence.
    - Agent task names and requested model/effort for the Explorer, reviewers, verifier, and Luna.
    - Plan-review and code-review rounds consumed, verdicts, open findings, and dispositions.
    - Branch, base/HEAD, diff fingerprint, Luna-owned paths, and protected changes.
    - Verification commands/results, deliberately unrun checks, and next action.
    It must not contain hidden reasoning, raw full logs, secrets, credentials, or private user data.
16. Treat the state file as an index, never as proof. Every resumed phase must refresh the plan revision, branch/HEAD, diff, relevant current files, and verification evidence. If approval evidence is absent, require renewed user approval before edits. If an agent thread is unavailable, spawn the same exact role with `fork_turns: "none"`, seed it from authoritative artifacts and the recorded ledger, and continue with the remaining review budget rather than resetting to round one.
17. Enforce the Explorer's read-only contract behaviorally and with fail-closed monitoring. Before and after every Explorer turn, capture and compare `HEAD`, `git status --short --untracked-files=all`, and the current diff fingerprint. The Explorer may run only non-mutating inspection commands; it may not run builds, tests, formatters, generators, or commands that create cache/state output. Stop and reconcile any unexplained delta before using its output.
18. State the enforcement limitation honestly: direct collaboration agents share the workspace, so this is a dedicated Explorer role plus prompt prohibition and worktree monitoring, not a filesystem-enforced read-only sandbox. Hard sandbox isolation would require additional runtime machinery that is outside the user-approved one-skill scope.

#### Implementation contract

19. After explicit implementation authorization, create or continue an appropriate task branch only when safe. Do not overwrite, revert, stage, or mix unrelated worktree changes.
20. Spawn one Luna implementer with agent type `worker`, `fork_turns: "none"`, model `gpt-5.6-luna`, reasoning effort `max`, and a stable implementation task name. Give it the complete approved-plan capsule, exact owned paths, protected paths, repository instructions, success criteria, and proportionate verification. Tell it that other agents or user edits may coexist and it must not revert them.
21. Keep implementation waves bounded by dependency and file ownership. Never run overlapping write-capable waves concurrently. Reuse the same Luna thread for implementation continuations and accepted fixes so it retains implementation context. If the thread is lost, create a replacement Luna with the recorded ownership and current repository evidence; do not infer completion from the prior worker report.
22. Resume the Explorer only after a coherent Luna wave has yielded. It must inspect the current plan, `git status`, `git diff`, changed call paths, and cited test/build output, then return only the material delta: implemented, missing, divergent, newly risky, uncertain, and the proposed next bounded handoff.
23. Send routine compiler/test defects directly back to Luna. Use the Explorer for failures only when they invalidate a plan assumption, cross ownership or architecture boundaries, affect security/persistence/platform contracts, survive two focused attempts, or require a user decision. This avoids turning the Explorer into another mandatory relay hop.
24. The manager still reviews the full effective change against the latest request, plan, and repository rules. Explorer output narrows attention but cannot replace current-file inspection, focused audit, tests, builds, or behavior tracing.

#### Adversarial code review and repair contract

25. After initial verification passes, spawn the code reviewer with agent type `default`, `fork_turns: "none"`, model `gpt-5.6-sol`, reasoning effort `xhigh`, and a distinct stable task name. Seed it with the latest request, approved plan path, current diff basis, repository review-rule paths, and exact verification evidence—not inherited Explorer conversation. Reuse only this reviewer for the bounded review loop.
26. Use the same exact `APPROVED`, `REQUEST_CHANGES`, and `NEEDS_REWORK` terminal verdicts and malformed-verdict fail-closed behavior as plan review. Every invocation consumes one of at most five code-review rounds. `APPROVED` converges; `REQUEST_CHANGES` enters disposition/fix/re-verification; `NEEDS_REWORK` stops and surfaces structural rework to the user. Never reset the budget when a reviewer thread is replaced.
27. Preserve every reviewer finding verbatim in the ledger. Ask the Explorer to map each finding to current code, plan language, user decisions, likely disposition, repair ownership, and required verification. The Explorer may recommend accept/rebut/escalate but may not filter findings or decide their disposition.
28. The manager adjudicates the ledger. Consolidate all accepted findings for a round into one Luna repair wave when ownership permits, then run one risk-based verification matrix for that wave rather than a broad suite after each individual finding.
29. Return the evidence-backed disposition and fresh verification to the same code reviewer when available. Stop on `APPROVED`; stop at round five with unresolved findings clearly reported and do not claim completion.
30. After code-review convergence, have the Explorer assemble a final traceability packet mapping request/plan criteria, implementation evidence, review findings, fixes, verification commands/results, unrun manual/platform checks, and residual uncertainty. It must not include an approval recommendation.
31. Spawn the final verifier with agent type `default`, `fork_turns: "none"`, model `gpt-5.6-sol`, reasoning effort `xhigh`, and a new task name distinct from every prior role. Seed it with authoritative paths and current evidence. It must independently inspect the repository rather than trusting the Explorer packet and must return exactly `APPROVED`, `REQUEST_CHANGES`, or `NEEDS_REWORK`; malformed output is not approval.
32. If the final verifier finds a material issue, reopen the same bounded code-review/repair loop when fewer than five code-review rounds have been consumed, then use another fresh final verifier after convergence. The repair and reviewer recheck consume the next code-review round; the final-verifier call does not silently create a new review budget. If the five-round budget is exhausted, report the unresolved issue and do not complete.

#### Manager completion and user communication

33. Before completion, the manager rereads the latest user request and subsequent constraints, verifies every named behavior and affected platform/call path, performs the required focused `docs/ai/audit.md` pass, and checks that every changed line traces to the request.
34. Report milestones to the user without making them relay routine agent messages. Ask the user only for genuine scope/product decisions, acceptance of unresolved risk, destructive/external authorization, or separately permissioned verification such as a device run or broad service fixture.
35. The final response must separate request/behavior verification from build/test verification and list unrun checks or remaining risks. The manager, not Explorer, Luna, or a reviewer, declares completion.
36. Stop after the verified implementation handoff by default. Never commit, push, merge, tag, bump versions, publish, or release unless the user's current request explicitly authorizes the particular action.

## Explorer Output Contract

At each material checkpoint, require a compact packet with these fields:

```text
Snapshot
Plan path/revision | branch@HEAD | current diff state | evidence freshness

Outcome
One sentence describing the material change since the prior checkpoint.

Acceptance delta
Implemented | missing | divergent criteria, with file/symbol evidence.

Knowledge delta
Verified facts | inferences | invalidated assumptions | uncertainties.

Review ledger delta
Finding | status | current evidence | recommended disposition | verification.

Decision required
None, or one concrete manager/user decision.

Next handoff
Owner | bounded outcome | owned/protected paths | invariant | focused verification.
```

Packets must be deltas rather than repeated plans, full diffs, raw logs, or directory dumps. A stale snapshot must be labeled stale and refreshed before it influences a decision.

## Technical Considerations

- **Exact-model enforcement**: Use explicit model and reasoning parameters for every spawned role. No silent fallback is allowed.
- **Reviewer independence**: Plan review, code review, and final verification use agents distinct from the Explorer and implementer. Reviewer prompts contain authoritative artifacts, not the Explorer's conclusions.
- **Concurrency**: The persistent Explorer may remain allocated, but write and inspection checkpoints are sequential. No Explorer inspection occurs while Luna is mutating the same tree, and no overlapping writers are permitted.
- **Context freshness**: Current files, diff, plan, user messages, and command results always outrank agent memory or the optional local capsule.
- **Cost control**: Use Explorer checkpoints only when knowledge materially changes. The expected substantial-task path is planning evidence, approved-plan capsule, post-implementation/review consolidation, and final traceability; routine progress and compiler errors bypass it.
- **Scope control**: The skill does not add a new runtime framework, manifest, installer, upgrade path, test harness, or family of workflow skills.
- **Safety**: The Explorer is contractually read-only, uses the dedicated Explorer role, and is surrounded by fail-closed worktree monitoring. Direct collaboration does not provide filesystem sandbox isolation, so the plan does not overclaim that guarantee.
- **Repository verification**: Existing focused audit, build, test, platform, no-device-by-default, and no-broad-fixture-without-approval rules remain binding.

## Edge Cases Considered

- **Implementation deferred after planning**: Preserve the approved plan; on resumption, reconstruct the Explorer from current sources before editing.
- **Explorer context lost or stale**: Spawn a new exact Sol `high` Explorer, mark old claims stale, and rehydrate from the plan, latest user constraints, branch/HEAD, current diff, state ledger, and evidence.
- **Plan reviewer, code reviewer, or Luna thread lost**: Spawn a replacement exact role from authoritative paths and the durable ledger. Preserve consumed review rounds, open findings, ownership, and verification state; never infer approval or reset a cap.
- **Exact model unavailable**: Stop and report the unavailable role; do not substitute.
- **User changes scope during implementation**: Pause affected edits. Use Explorer for an impact map, update/re-review the plan when the change is substantive, and obtain renewed user approval.
- **Dirty worktree or concurrent user edits**: Record protected paths and current ownership. Do not revert or absorb unrelated changes; stop if safe isolation is not possible.
- **Reviewer disputes Explorer**: The reviewer remains independent. The manager checks current source evidence and records a reasoned disposition; Explorer has no tie-breaking authority.
- **Repeated routine failure**: Route the first focused failures directly to Luna. Escalate to Explorer/manager after two unsuccessful repair attempts or earlier when a contract/scope issue emerges.
- **Plan review reaches round five**: Surface unresolved findings and require a user decision before implementation; do not silently reset the reviewer.
- **Code review reaches round five**: Report unresolved findings and do not claim completion.
- **Fresh final gate finds a new issue**: Reopen the remaining code-review budget; never bypass the cap by repeatedly spawning final reviewers.
- **Trivial task**: Keep the same authority and approval boundaries, but use one concise Explorer pass and stop adversarial loops as soon as the independent reviewer reports clean.
- **Release requested later**: Require explicit scope and authorization in that later request; the skill does not automatically invoke any existing release skill.
